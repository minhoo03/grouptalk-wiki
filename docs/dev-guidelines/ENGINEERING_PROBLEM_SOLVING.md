# Engineering Problem-Solving Convention

> 핵심 원칙: 해결책부터 정하지 않는다. 문제의 목적·실패 원인·불변 조건을 정의하고, 작은 실험으로 설계를 검증한 다음 구현한다.

## 1. 적용 범위

- **권장:** 신규 기능의 구조 설계, 상태·데이터 흐름 변경, 성능 및 동시성 문제, 반복되는 버그, 기술 도입, 사용자 경험에 영향을 주는 변경
- **간소화 허용:** 영향 범위가 작은 문구·스타일 수정, 재현 및 수정 방법이 이미 검증된 단순 버그. 필요 이상의 설계 문서나 추상화를 강요하지 않는다.
- **반복 적용:** 절차는 한 번만 진행하는 직선형 과정이 아니다. 가설이 틀리거나 검증에 실패하면 원인 분석과 문제 재정의로 돌아간다.

## 2. 문제 해결 프로세스

### 2.1 문제 발견: 현상과 목적을 분리한다

- 현재 관찰된 현상, 기대 동작, 사용자·제품에 미치는 영향을 작성한다.
- 기술 이름이 아닌 **해결해야 할 문제**로 서술한다.
- 완료 기준은 가능하면 관찰하거나 측정할 수 있어야 한다.
- **지양:** “SWR을 도입해야 한다.”
- **권장:** “화면 이동 후 오래된 요청 결과가 최신 검색 조건을 덮어쓰지 않아야 한다.”

### 2.2 원인 가설 및 최소 실험: 가장 작은 검증부터 시작한다

- 현상의 원인에 대한 가설을 명시하되, 확인되지 않은 사실을 확정하지 않는다.
- 이 단계의 설계는 확정안이 아니라 검증할 가설이다. 실패하면 원인 분석과 문제 재정의로 돌아간다.
- 복잡한 변경에서는 최소 두 가지 대안을 검토하고 각각의 해결 범위, 복잡도, 위험, 롤백 방법을 적는다.
- 필요한 경우 최소 구현(PoC)으로 가장 중요한 가정 하나부터 검증한다.
- 새로운 기술이나 추상화보다 기존 플랫폼과 라이브러리의 책임을 먼저 활용한다.

### 2.3 실패와 원인 분석: 증상 대신 메커니즘을 조사한다

- 재현 조건, 로그, 요청 순서, 상태 변화, 호출 경로 같은 **증거**를 확보한다.
- 브라우저·비동기 순서에 의존하는 실패는 [웹 테스트 실패 증거 컨벤션](./WEB_TEST_FAILURE_EVIDENCE.md)에 따라 기대 결과와 실행 증거를 연결한다.
- 언제·어디서·누구와 공유되는 상태 또는 실행 환경인지 확인한다.
- “어떻게 우회할까?”보다 “왜 이런 일이 가능한 구조인가?”를 먼저 질문한다.
- 재현 없이 임시 우회책을 누적하지 않는다.

### 2.4 문제 재정의: 실패에서 불변 조건을 추출한다

- 실패한 이유를 시스템이 반드시 지켜야 하는 **불변 조건**으로 다시 서술한다.
- 불변 조건과 상황에 따라 선택할 수 있는 조건을 구분한다.
- 변화가 잦은 것과 드문 것, 사용자별로 독립적이어야 하는 것과 공유해도 되는 것을 분리한다.
- 원래 사용하려던 기술이나 구현 방식을 목표로 착각하지 않는다.

### 2.5 책임과 경계 설계: 누가·어디서·언제 처리하는가

- 데이터·상태·정책·부작용·연산에 책임이 있는 계층을 식별한다.
- 다음 질문으로 구조를 점검한다.
  - **누가:** 상태와 규칙의 단일 책임자는 누구인가?
  - **어디서:** 서버·브라우저·Worker·컴포넌트 중 적합한 위치는 어디인가?
  - **언제:** 매 렌더·매 요청·변경 시점·배포 시점 중 어느 때 수행해야 하는가?
  - **무엇을 공유하는가:** 사용자 간 격리해야 할 것과 재사용 가능한 것은 무엇인가?

### 2.6 해결책 구현: 적절한 도구를 조합하고 최소 범위로 변경한다

- 선택한 방식이 불변 조건을 모두 만족하는지 구현 전에 확인한다.
- 도구가 이미 잘하는 일을 자체 구현하지 않는다.
- 대안 대비 선택 이유와 트레이드오프를 짧게 남긴다.
- 영향 범위가 큰 변경은 되돌릴 수 있는 단위로 나눠 구현한다.
- 최적화는 측정된 병목을 대상으로 하며 유용성이 낮은 복잡한 기능은 채택하지 않는다.

### 2.7 검증 및 기록: 동작이 아니라 문제 해결을 확인한다

- 정상 흐름뿐 아니라 관련 있는 경계 조건, 예외, 느린 네트워크, 중복 요청, 다중 사용자 시나리오를 검증한다.
- 최초에 정의한 완료 기준에 맞춰 결과를 확인한다.
- 변경 전후 수치가 있다면 비교하고, 없다면 재현 가능한 테스트 증거를 남긴다.
- 해결하지 못한 위험, 재검토 조건, 결정 근거를 작업 기록이나 PR에 남긴다.

## 3. 설계 의사결정 기록

복잡한 변경에서는 아래 항목을 짧게 채운다. 작은 변경은 필요한 항목만 사용한다.

```md
## Problem

- 현상:
- 기대 결과 / 사용자 가치:
- 완료 기준:

## Investigation

- 확인된 사실과 근거:
- 원인 가설 / 미확인 사항:
- 반드시 지킬 불변 조건:

## Design

- 대안 A / 장단점:
- 대안 B / 장단점:
- 선택안과 이유:
- 책임 분리 (상태/로직/데이터/부작용):
- 트레이드오프 / 위험:

## Experiment & Validation

- 가장 작은 검증 방법:
- 실패하면 수정할 가정:
- 테스트 (정상/예외/경계):
- 검증 결과:
- 추후 재검토 조건:
```

## 4. 예시: 이전 검색 요청이 최신 결과를 덮어쓰는 문제

**문제 발견:** 검색어 B로 변경했는데 이전 검색어 A의 결과가 나중에 도착해 화면을 덮어쓴다. 완료 기준은 현재 검색어에 대응하는 결과만 보여 주는 것이다.

**초기 가설:** 입력에 debounce를 적용해 API 호출 횟수를 줄이면 문제를 완화할 수 있다고 가정한다.

**실패와 원인:** 요청 수는 줄었지만 A 요청보다 B 요청이 먼저 완료될 수 있다. 완료 순서가 요청 순서와 다르다는 경쟁 상태가 근본 원인이다.

**문제 재정의:** 목표는 호출 빈도 감소가 아니라 현재 검색 조건과 일치하는 응답만 화면에 반영하는 것이다.

**해결:** 검색 조건을 요청 식별자(query key)와 연결하고, 조건이 바뀌면 이전 요청을 취소하거나 오래된 결과가 반영되지 않게 한다. 호출 횟수가 실제 병목이라면 debounce를 별도 최적화로 적용한다.

**검증:** A 응답을 의도적으로 늦추고 B 응답을 먼저 도착시켜도 최종 화면에는 B 결과만 표시되는지 테스트한다.

## 5. AI 에이전트 작업 지침

1. 코드를 작성하기 전에 문제, 완료 기준, 확인된 사실과 가정을 구분해 제시한다.
2. 복잡한 설계에서는 대안 최소 두 가지, 선택 근거, 트레이드오프, 검증 계획을 제시한다.
3. 프로젝트 코드에서 확인할 수 없는 동작은 사실처럼 단정하지 않는다. 관련 파일 또는 실행 근거를 명시한다.
4. 오류가 나면 무작정 패치를 추가하지 않고 재현 → 원인 → 실패한 가정 → 문제 재정의 순서로 검토한다.
5. 구현 후에는 완료 기준과 실패 시나리오를 검증하고 검증하지 못한 사항을 명시한다.
6. 간단한 변경에는 절차를 압축해서 적용한다. 과도한 추상화나 불필요한 도구 도입은 피한다.
7. 최종 기술 선택과 중요한 트레이드오프의 승인 책임은 개발자에게 있다. AI는 대안 탐색·구현·테스트를 지원한다.
