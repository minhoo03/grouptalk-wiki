# AI와 사람이 함께 만드는 테스트 설계 대화

이 문서는 AI에게 테스트 코드를 바로 생성시키는 프롬프트가 아니다. 사람이 사용자 흐름과 위험을 설명하고, AI가 테스트 계층과 사례를 제안한 뒤, 사람이 범위를 승인·수정하고 함께 실행 결과를 확인하기 위한 대화 양식이다.

순수 함수, 컴포넌트·기능, E2E 테스트에 같은 흐름을 사용한다. 다만 단순한 변환 함수처럼 판단할 내용이 적으면 축약형을 사용한다.

현재 보일러플레이트에는 테스트 도구가 설치되어 있지 않다. 아래 Vitest, Testing Library와 Playwright는 도입 시의 기본 선택이며, 실제 package와 script를 추가하고 실행하기 전에는 테스트가 통과한다고 기록하지 않는다.

## 핵심 규칙

### 규칙

1. AI는 첫 응답에서 테스트 코드를 작성하지 않고, 이해한 흐름·위험·테스트 계층·최소 사례를 먼저 제시한다.
2. 사람은 제안된 사례를 승인, 수정, 제외하고 우선순위를 결정한다.
3. AI는 승인된 범위만 구현하고 가장 작은 관련 테스트부터 실행한다.
4. 사람과 AI는 실패 원인, 수정 전후 결과, 남은 미검증 범위를 함께 확인한다.
5. 테스트는 내부 함수 호출 횟수보다 사용자가 관찰하는 동작 또는 공개된 입력·출력 계약을 검증한다.

### 이유

AI가 요구사항을 잘못 이해한 상태에서 코드를 먼저 만들면 테스트 수는 많아져도 중요한 위험을 놓치거나 구현 세부사항을 고정하기 쉽다. 코드 작성 전에 테스트 목적과 계층을 합의하면 사람이 판단의 주체로 남고, AI는 사례 탐색과 반복 구현을 빠르게 보조할 수 있다.

Vitest는 테스트를 입력과 출력의 계약으로 다루고 Arrange-Act-Assert 구조와 한 테스트당 하나의 동작을 권장한다. Testing Library는 실제 사용자가 요소를 찾는 방식에 가까운 role과 accessible name을 우선한다. Playwright는 사용자에게 보이는 동작을 격리된 브라우저 환경에서 검증하고 user-facing locator를 사용할 것을 권장한다.

### 적용 조건

- 새로운 기능의 테스트 범위를 정할 때
- 발견한 버그를 회귀 테스트로 남길 때
- 함수, 컴포넌트, E2E 중 어디에서 검증할지 애매할 때
- 비동기 순서, URL, 브라우저 저장소처럼 여러 경계가 만날 때
- AI가 제안한 많은 사례에서 제한 시간 안에 구현할 범위를 골라야 할 때

### 예외

- 입출력이 명확한 단순 순수 함수는 아래 축약형으로 시작할 수 있다.
- 문구 한 글자처럼 동작 계약이 바뀌지 않는 변경에는 이 양식을 강제하지 않는다.
- 긴급한 회귀 수정에서는 먼저 실패를 재현할 수 있다. 다만 수정 전에 재현 조건과 기대 결과는 사람과 AI가 확인한다.

## 테스트 계층을 고르는 기준

같은 사례를 모든 계층에서 반복하지 않는다. 세부 분기는 가장 낮고 빠른 계층에 두고, 실제 통합에서만 생기는 위험만 높은 계층에 둔다.

| 계층          | 적합한 대상                                                      | 도입 시 기본 도구        | 관찰할 결과                                  |
| ------------- | ---------------------------------------------------------------- | ------------------------ | -------------------------------------------- |
| 함수·단위     | 계산, parser, reducer, adapter, 상태 전이                        | Vitest                   | 입력에 따른 반환값, 오류, 외부 경계 호출     |
| 컴포넌트·기능 | 입력, 클릭, loading, 오류, 빈 상태, 접근성                       | Vitest + Testing Library | 사용자가 찾고 조작하고 확인하는 화면 상태    |
| E2E           | 페이지 이동, history, reload, focus, storage, 실제 브라우저 통합 | Playwright               | 핵심 사용자 흐름의 최종 결과와 브라우저 동작 |

Playwright는 Next.js 개발 서버 또는 빌드 서버를 실제 브라우저에서 열어 App Router의 핵심 흐름을 검증할 수 있다.

예를 들어 검색 결과의 정렬 함수는 Vitest, 검색 버튼과 오류 안내는 Testing Library, URL을 공유하거나 뒤로가기로 검색 조건을 복원하는 흐름은 Playwright가 맡는다.

## 전체 대화 양식

아래 내용을 작업 대화의 시작점으로 복사한다. 모르는 항목은 `미정`으로 두고 AI가 사실과 가정을 구분해 제안하게 한다.

```md
[1. 사람이 제공하는 작업 맥락]

- 작업 또는 버그:
- 사용자가 시작해서 끝내는 흐름:
- 반드시 지켜야 하는 결과:
- 가장 손실이 큰 실패:
- 이미 발견한 경계 사례:
- 실제 외부 경계(API, URL, storage 등):
- mock으로 대체해도 되는 경계:
- 변경 허용 범위:
- 변경하면 안 되는 범위:
- 이미 있는 관련 테스트:
- 시간 제한:

[2. AI의 첫 응답 — 아직 테스트 코드 작성 금지]

1. 이해한 사용자 흐름
2. 관찰 가능한 성공·실패 결과
3. 권장 테스트 계층과 선택 이유
4. 최소 테스트 사례 표
5. 실제로 연결할 경계와 mock할 경계
6. 사실, 가정, 확인이 필요한 질문
7. 이번 범위에서 제외할 사례와 이유
8. 승인 후 실행할 최소 명령

테스트 사례 표 형식:

| ID  | 계층 | Given | When | Then | 이 사례가 막는 위험 |
| --- | ---- | ----- | ---- | ---- | ------------------- |

[3. 사람의 범위 결정]

- 승인할 사례 ID:
- 수정할 사례와 이유:
- 제외·연기할 사례와 이유:
- 먼저 실패를 재현해야 하는 사례:
- 최종 테스트 이름:
- 코드 작성을 승인함: 예 / 아니오

[4. AI의 구현과 실행]

- 승인된 사례만 구현한다.
- Arrange-Act-Assert가 읽히게 작성한다.
- 컴포넌트와 E2E에서는 role, label, accessible name을 우선 사용한다.
- 여러 테스트를 위한 추상화는 실제 중복과 정책이 확인될 때만 만든다.
- 가장 작은 관련 테스트를 먼저 실행하고, 통과하면 필요한 상위 검증을 실행한다.
- 실패하면 결과를 숨기지 말고 관찰 사실과 원인 가설을 분리한다.

[5. 사람과 AI의 결과 확인]

- 추가·수정한 테스트:
- 수정 전 재현 결과:
- 수정 후 실행 명령과 결과:
- 테스트가 방지한 경계 사례:
- AI 제안 중 사람이 수정·거절한 판단:
- 아직 검증하지 못한 범위와 위험:
- 필요할 때만 남길 실패 증거 위치:
```

## AI 첫 응답의 최소 사례 수

기본은 핵심 흐름 하나당 다음 중 필요한 사례 3~5개만 제안한다.

1. 대표 성공 경로
2. 손실이 가장 큰 실패 경로
3. 빈 값 또는 경계값
4. 비동기 순서 역전이나 중복 실행
5. 실제 브라우저에서만 생기는 경로

다섯 가지를 항상 모두 만들지 않는다. 요구사항과 위험으로 설명할 수 없는 사례는 제외한다. AI가 더 많은 사례를 발견했다면 `추가 후보`로 분리하고 사람의 승인 없이 구현하지 않는다.

## 대화 예시

사용자가 검색 결과 화면의 뒤로가기를 수정한다고 가정한다.

```md
[사람]

- 흐름: 검색어 입력 → 결과 확인 → 상세 진입 → 뒤로가기
- 반드시 지킬 결과: URL, 입력값, 결과가 이전 검색 조건으로 복원된다.
- 가장 큰 실패: 화면 입력값과 URL은 복원됐지만 다른 결과가 표시된다.
- 외부 경계: URL searchParams와 검색 API
- 시간 제한: 90분

[AI의 설계안]

| ID  | 계층     | Given                   | When              | Then               | 위험              |
| --- | -------- | ----------------------- | ----------------- | ------------------ | ----------------- |
| U1  | 단위     | 잘못된 page 값          | query parser 실행 | 기본 page로 정규화 | 잘못된 URL 입력   |
| C1  | 컴포넌트 | 검색 응답이 늦음        | 새 검색어 입력    | 최신 결과만 노출   | 응답 순서 역전    |
| E1  | E2E      | 검색 결과에서 상세 진입 | 브라우저 뒤로가기 | URL·입력·결과 복원 | history 통합 실패 |

API 500 오류는 컴포넌트 테스트에서 이미 검증하므로 E2E에서 중복하지 않겠습니다.

[사람의 결정]

- U1, C1, E1 승인
- E1에서는 결과 첫 항목까지 확인
- 검색 API의 모든 오류 코드는 이번 범위에서 제외
- 코드 작성 승인
```

이 대화는 `왜 E2E가 필요한가`, `무엇을 중복하지 않았는가`, `사람이 어떤 범위를 결정했는가`를 함께 남긴다.

## 축약형

단순한 함수 또는 작은 회귀 테스트에는 다음만 확인한다.

```md
- 계약: 어떤 입력에 어떤 출력 또는 오류가 필요한가?
- 경계값: 가장 중요한 빈 값·최솟값·최댓값은 무엇인가?
- 테스트 이름: 사용자가 읽을 수 있는 동작 문장인가?
- 실행: 어떤 최소 명령으로 실패와 통과를 확인할 것인가?
- 승인: 이 범위로 코드를 작성해도 되는가?
```

## 피해야 할 대화와 테스트

- 요구사항 확인 전에 AI가 테스트 20개를 한 번에 작성한다.
- `useState` 호출 횟수, 내부 함수 이름, CSS class처럼 사용자가 관찰하지 않는 구현을 고정한다.
- 같은 오류 분기를 단위, 컴포넌트, E2E에서 모두 반복한다.
- snapshot 하나로 핵심 사용자 동작을 대신한다.
- 실제 구현을 그대로 복제한 mock과 assertion으로 통과만 확인한다.
- 불안정한 테스트를 timeout, retry, 임의 대기로 숨긴다.
- 실행하지 않은 테스트를 통과했다고 기록한다.
- 사람이 승인하지 않은 리팩터링이나 테스트 유틸까지 함께 만든다.
