# Git 브랜치 규칙

이 저장소는 개인용 보일러플레이트이므로 장기간 유지하는 `dev` 브랜치나 개인별 중간 브랜치를 기본값으로 만들지 않는다. `main`과 짧게 유지되는 작업 브랜치를 사용한다.

## 1. 브랜치 역할

### `main`

- 언제든 설치와 프로덕션 빌드가 가능한 기준 브랜치
- 검토와 현재 프로젝트에서 실행 가능한 검증을 마친 변경만 반영
- 직접 push 또는 PR 사용 여부는 저장소 운영 방식에 맞추되, 위험한 변경은 PR을 권장

### `<type>/<short-description>`

하나의 작업 목적을 담는 짧은 수명의 브랜치다.

```text
feat/login-oauth
fix/duplicate-submit
refactor/document-editor
docs/react-conventions
chore/update-dependencies
```

브랜치 이름은 영문 소문자와 kebab-case를 사용하고, 구현 방식보다 작업 목적을 표현한다.

## 2. 작업 흐름

1. 작업 범위와 완료 조건을 정한다.
2. `main` 최신 상태에서 작업 브랜치를 만든다.
3. 하나의 목적에 맞는 변경과 검증을 수행한다.
4. 변경 이유와 실제 검증 결과를 리뷰한다.
5. `main`에 반영한 뒤 작업 브랜치를 정리한다.

현재 기본 검증은 다음과 같다.

```bash
pnpm check
```

테스트나 lint 도구를 추가한 프로젝트에서는 해당 명령도 검증에 포함한다. 설정되지 않은 검증을 통과했다고 기록하지 않는다.

## 3. 범위 관리

- 기능 변경과 관계없는 대규모 rename을 같은 브랜치에 섞지 않는다.
- 기능, 의존성, 문서가 하나의 사용자 결과를 위해 함께 필요하면 같은 작업에 포함할 수 있다.
- 긴급 수정도 원인과 검증을 생략하지 않는다.
- 여러 사람이 공유하는 브랜치를 rebase하거나 force push하기 전에 협의한다.

## 4. 선택 가능한 운영 방식

릴리스 주기, 여러 배포 환경 또는 대규모 팀 통합 때문에 `dev`, release branch가 실제로 필요해지면 추가할 수 있다. 보일러플레이트 단계에서는 미래 운영을 예상해 미리 만들지 않는다.
